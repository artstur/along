# 用户设置页

## 1. 目标与范围

Along iPhone App 缺一个统一入口：用户要设置昵称、查看并管理数据源授权、确认与服务端的配对与连接状态，只能在各个功能页里找。设置页把这三件事收在一处，并复用既有流程，不新造连接逻辑。

本单范围（对应工单 TASK-88）：

- 从 App 内进入设置页，页面上能看到昵称、数据源、Along 服务三段与各自当前状态。
- 昵称可设可改，持久化在 App 内；改昵称不影响 UID 与配对关系。
- 数据源沿用既有授权流程（Apple Health 走原生 HealthKit 桥接，OKX 走既有设备来源流程），失败时显示实际状态并可重试。
- 服务端沿用既有配对与连接检查流程；未配对用户可在设置页完成配对，已配对用户升级后继续可用。

不在本单范围：周六晨起称重提醒（另立需求）；服务端保存昵称（见 §6 待确认项）。

## 2. 昵称的归属规则

昵称是显示名，不是身份。它复用既有用户身份，不另建账号体系。

归属粒度是「已核验的 Host + UID」这一对身份，作用域键写作 `${host}|${uid}`：Host 取
`along.event-connection.v1` 里核验过的 `bindingOrigin`（归一化到 scheme/host/端口），UID 取该
记录里的 `userId`。两个身份要素缺一不可——只看 UID 不够，因为两台不同的 Mac 可能回传同一个 UID。

| 情形 | 昵称归属 | 表现 |
| --- | --- | --- |
| 尚未连上任何 Host | 记在本机桶（`\|`） | 本机可见 |
| 已连上 Host 且认得出 UID | 属于该 Host + 该 UID（`${host}\|${uid}`） | 只有这一对身份可见 |
| 已连上 Host 但 Host 不认 UID（旧协议） | 属于该 Host（`${host}\|`） | 只有这台 Host 可见 |
| 配对确认身份后 | 从本机桶认领到该身份 | 昵称跟着走，UID 与配对关系不动 |

因此：

- 同一台 Host 换用户（UID 变了）→ 看不到上一个人的昵称，也不会覆盖它。
- 换一台 Host（哪怕回传同一个 UID）→ 看不到另一台 Host 的昵称。
- 两台都不回传 UID 的旧协议 Host → 各自按自己那台 Host 分桶，不共用一条昵称。
- 换回原来那台 Host（UID 相同）→ 拿回自己上次保存的昵称。
- 正在输入、还没保存的草稿也记着它属于哪一对身份：换绑之后不跟着飘到另一台 Host，也不会被误存进新身份。

旧版（v1）记录只有一条昵称、只按 UID 区分、没有 Host 维度，升级后先放进「只有 UID」的旧桶，
由 UID 对得上的身份认领；UID 对不上就留在旧桶里，不给别人的身份。

三条硬约束：

- **改昵称不改 UID。** 昵称记录与身份记录分开存放，写昵称不碰 `along.event-connection.v1`，也不碰配对凭据。
- **改昵称不破坏配对。** 配对关系、token 与绑定作用域都不受昵称操作影响。
- **昵称不跨身份泄漏。** 换 UID 或换 Host 都看不到别人的昵称。

实现见 `web/user-profile.mjs`（纯逻辑）与 `web/app.mjs` 的存取部分。

## 3. 入口

顶部栏右侧的个人入口就是设置入口：显示昵称；没设昵称时显示身份标识；两者都没有就显示「设置」。设置页有返回按钮，返回到进入前的那一页。

入口放在所有页面的顶部栏（含首页、目标详情、任务详情），因为这三项都是跨目标的全局状态，放在某一页里就找不到。

## 4. 设置页的三段

一屏只服务一个主要任务，所以三段各自独立、互不嵌套。

### 4.1 昵称

一个输入框加保存按钮。输入做清洗：去控制字符、去首尾空白、最长 24 字。清空昵称等于删除记录本身，不留空记录。

下方一行说明当前身份（`u_xxxxxxxx`）或说明「还没配对，昵称先存在本机」。

### 4.2 数据源

列出 App 已支持的数据源，每项显示当前状态与一个操作按钮：

- **Apple Health**：状态来自原生桥接的真实读取状态（未连接 / 检查中 / 读取失败 / 无可读取记录 / 演示数据 / 已导入 / 已连接），操作走既有的 `connect-health` 流程——原生弹层选类型、预览、导入。
  - 「已连接」只在原生真的读回了数值时才算：选了类型却读不到任何数值时显示「无可读取记录」，并提示检查系统健康权限或「健康」App 里有没有记录，同时给出「重试」。
  - 读取失败（原生读数报错）要在当前这一页立刻显示「读取失败」，不能停在「检查中」等用户重开页面才看见。
- **OKX**：按目标授权，不是全局开关。设置页显示「本人获推荐的目标」那个带 OKX 数据源的目标（当前选中的目标带 OKX 时优先用它），不用先切目标才管得到。
  只有**活跃**目标能接 OKX（Host 要求目标与修订都活跃）：只剩已归档目标保留推荐时不给连接入口，免得给出连不上的按钮。
  状态取既有设备来源查询结果，进入/重开设置页都要回读一次原生——Host 可能已经收过摘要，原生也可能已排队撤回，缓存值会过期。
  - 已连接且 Host 已收到摘要：显示「已连接 / 只读 · Mac 已收到摘要」。
  - 已连接但还没收到：显示「只读 · 等待同步到 Mac」。
  - 本机已停采集、撤回还排着队等 Host 收尾：显示「已停止采集 / 本机已停止采集，撤回仍待 Host 接收」，不与「从没连过」混成同一句话。
  - 撤回已拿到 Host 回执（原生转 stopped）：显示「本机已停止采集，撤回已获 Host 接收」——这说的是撤回拿到了回执，不是最后一份摘要拿到了。
  操作走既有的 `event-okx-connect` 流程。

操作按钮的文案跟着状态走：未连接是「连接」，已连接是「管理」，读取失败与读不到记录是「重试」。授权被拒或被撤销时显示实际状态，不假装已连接。

### 4.3 Along 服务

一张状态卡加配对入口：

- 未配对：显示「未配对」并直接给出配对表单（服务地址 + 一次性连接码）。
- 已配对且检查通过：显示「已连接」与服务地址。
- 已配对但检查没通过：显示「已配对」并按可观测结果分出原因——
  - 凭据失效（HTTP 401/403）：提示需要重新配对；
  - 服务暂不可用（HTTP 5xx，Agent 未就绪）：提示稍后重试；
  - 连不上 Host（请求没拿到状态码）：提示查网络与服务地址。
  卡片不说「连接需处理」——配对本身已经成了，说「连接需处理」会让用户以为要重配一遍。
  「重试连接」复用现有凭据重新检查，不换 token、不重新配对。
- 连接中断时额外给出「只更新服务地址」表单。

配对走既有 `/pair` 与原生 Keychain 凭据存储；「重试连接」走既有 `/connection/status` 检查。
配对成功但检查没通过时，提示语要说实话：报「已配对，但服务暂不可用，可以在设置里重试」，不报「已连接 Along」。
冷启动时凭据已失效（401）也要当场看见：连接检查一有结果就重画设置页，不停在「检查中」等用户手动点重试。

HTTP 状态码由原生桥透传到网页层（`AgentBridgeError.httpStatus` → 错误对象的 `status`），网页据此分类；
拿不到状态码时按「连不上 Host」处理——宁可说保守的话，不把服务说成已连接。

## 5. 验收标准

以 iOS 实际操作为准：

- 能从 App 内进入设置，看到三段与当前状态。
- 新用户能设昵称，已有用户能改；重启后显示最近一次保存的值；原 UID 仍有效，配对关系不变。
- 数据源能授权、能连接；拒绝授权、撤销授权或连接失败时页面显示实际状态并可重试。
- 未配对用户能在设置页完成配对与连接；已配对用户升级后能继续连接；配对失败或连接中断有明确状态并可重试。

自动化覆盖见 `test/user-profile.test.mjs`（昵称规则）、`test/app-settings-page.test.mjs`（页面行为，含重启后仍显示）与 `test/ats88-review-regressions.test.mjs`（独立复核缺陷的回归：第一轮四项 + 第二轮五个场景，含隔离真实 Host 的配对与重试）。

## 6. 待确认项

- **服务端是否也要保存昵称。** 本轮昵称只存在 App 内，Mac 侧的 Agent 看不到它。若要让 Agent 用昵称称呼用户，需要服务端存一份并随身份下发，这要动 Host 与 Along Agent 的接口与存储，属于另一轮改动。
- **昵称是否需要同步到其他设备。** 同上，取决于上一项。
- **OKX 在设置页的入口粒度。** 本轮显示「本人获推荐的目标」那个带 OKX 数据源的目标（当前选中的目标带 OKX 时优先用它）。若以后一个用户有多个带 OKX 的目标，这里要能选；是否改成按设备聚合，等目标模型定下来再说。
- **原生 HTTP 状态码透传。** 本轮已把状态码从原生桥带到网页层（`AlongShellView.swift` 的 `AgentBridgeError.httpStatus`）。若将来还有别的原生错误需要分类，走同一条路。

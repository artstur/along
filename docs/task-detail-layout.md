## 范围与实现

- 事件工作台按目标 → 动态任务 → 连接数据源排列。现有目标聊天只保留直接对话。
- 使用稳定的目标和任务身份进入现有工作台的任务详情，推荐按两者精确归属，保留来源与分别过期状态、方案反馈。通知进入同一详情。
- 卡片不展开内部提醒依据；提醒规则、需要补充的信息和真实系统安排仍在详情。执行时间与提醒时刻分别说明。
- 执行次数由宿主可证明的任务执行证据投影，不能用模型调用、版本、消息数或重试计数。推荐研究、提醒任务、实际生活动作按各自任务语义判定；真实预约／徒步不能因提醒已发而写作已完成。开发验收来源不计自然业务执行。
- 旧缓存和旧消息保持兼容；缺少可信执行证据时不伪造次数。原目标、任务、排程、配对、用户对话与推荐正文不变。

## 任务完成确认与历史任务入口

主分类 ui，依赖服务端既有 `task.completed` 协议与 `task_updated` 同步项；服务端基线为 Along Agent `src/along/inbox.ts` 的完成事实分支。本轮只补「完成」确认键与「历史任务」入口，不新增事件类型、不改事件 schema 与双端向量、不新增产品主模块、采集与凭证。

问题：任务卡没有确认完成的入口，已完成的任务和未完成的任务混在同一张列表里，用户看不到「这件事已经做完了」。根因在服务端：完成事实只写了任务状态，没有发出 `task_updated` 同步项，客户端拿不到新快照，状态无从更新。

范围：

- 客户端 `web/event-workspace.mjs` 增加 `completeTask(taskId)` 与 `pendingTaskCompletions()`：复用既有 `along.message` / `task.completed` 信封（载荷只带 `kind`、`task_id`、`completed_at`，`envelope.kind` 必须等于 `payload.kind`），入队后由既有的 `sync()` 投递并拉取同步项。状态只来自服务端快照，客户端不乐观改状态。
- 客户端 `web/app.mjs`：任务卡右侧栏增加「完成」键（仅 open 任务，与「查看详情」同为12px浅灰透明文字、无下划线，状态与入口仍右对齐）；点开是确认层，取消不发任何请求、状态与列表完全不变，确认才发出完成事实；任务区标题行增加同级「历史任务」入口，复用同一份目标快照里的任务、只列 `status==='done'`；「动态任务」只列 open。
- 服务端 `along-superagent/src/along/inbox.ts`：完成事实落库后补发带 `goal_id` 的 `task_updated` 同步项（`status='done'`、`revision` 与任务当前版本一致）。`goal_id` 必带——客户端只对带 `goalId` 的同步项应用目标快照，缺它就拿不到新状态。
- 周期任务语义不变：带每日安排的 open 任务走服务端既有的「完成本次并续排」分支，任务仍 open、不进历史任务；该分支本就发出 `status='open'` 的同步项，客户端不自行判断或改状态。

验收：open 任务卡出现「完成」键、done 任务卡不出现；取消不发任何请求且列表不变；确认只发一条 `task.completed`（`task_id`、`goal_id` 正确，`completed_at` 为确认时刻），服务端接受后卡片状态变为「已完成」；该任务从「动态任务」移出、在「历史任务」可见，刷新或重启后仍是「已完成」；改前就是 done 的历史任务也能在「历史任务」看到；周期任务点完成不误关任务（仍 open、执行次数 +1）；服务端完成事实产生 `task_updated` 同步行且 `/sync` 快照里该任务为 done。重复提交不累加执行次数，待发队列里已有该任务的 `task.completed` 时不再显示「完成」键。

本子任务实测：服务端 `pnpm exec vitest run tests/along-inbox.spec.ts` 24 项通过（新增完成事实同步行一项，回退修复后该项重新失败）；`pnpm check` 1928 项通过、1 跳过（typecheck 与 build 同跑通过）。客户端 `npm run check` 863 项：860 通过、0 失败、3 跳过（含新增 8 项：完成事实只入队一次、重复提交被拒、服务端快照驱动状态、卡片与历史任务入口、确认层取消不发请求、确认只发一条）。`npm run build` 22 文件，web/dist/iOS 逐字节一致。Web 版本 `?v=95`、ServiceWorker `along-shell-v95`、原生 `build=95`，`Info.plist` 的 `CFBundleVersion` 未提高。未部署正式 Host、未安装手机；周期任务的续排与执行次数沿用服务端既有语义，本轮未改。

## 独立验收退回后的三个修复

独立验收（附件 `task76-verify-harness.mjs`，真实 Host + 真实 Along Agent + SQLite + Chromium）复现了三个缺陷，本节记录修法与复测证据。

### 历史分页漏项

目标快照有界（最多 200 条任务），同一目标有 201 条已完成任务时，最旧一条不在快照里，页面也没有继续读取的入口。修法是**按需分页**，不放大每次同步的目标快照：

- 服务端既有 `GET /tasks` 增加 `goal_id` 过滤（`src/along/api.ts`），游标翻页不变。
- Host 的既有 `POST /sync` 接受可选的 `tasks_page` 请求并把这一页挂在应答里（`host/agent-host.mjs`）。**手机到 Host 的路径白名单不新增端点**（`docs/iphone-ca-profile-design.md` §2.1 的「12+4 条、M6 零新增零删除」是契约，见 `test/ios-connection-migration.test.mjs`），因此翻页请求随既有 `/sync` 一起走。
- 客户端 `web/event-workspace.mjs` 的 `loadHistoryPage()` 校验这一页（与目标快照同一套任务校验 `safeTaskPage`），`historyTasks()` 把快照里的已完成任务与翻页取回的部分按 id 去重合并；`web/app.mjs` 在进入历史任务入口时自动翻页，直到出现快照之外的历史任务或翻到尽头，仍有更早的才显示「加载更早的任务」。

### 周期任务完成文案与实际行为不一致

服务端对有每日安排的 open 任务走「完成本次并续排」，任务仍 open、不进历史任务；确认层却统一写「会移入历史任务」。修法：确认层按任务的每日安排区分——周期任务写「确认后完成本次安排，任务会继续按原计划续排，仍在动态任务里」，普通任务才写「会移入历史任务」。判断沿用客户端既有的 `recurringPlan`（服务端 `reminderPlan` 只在存在每日安排时才带时区，两者同源）。

### 写入已受理而同步返回 503 时重复提交

客户端只把「还没送达队列」的完成事实算作已提交；`/events` 已被受理、同步却失败时，队列已清空，页面仍是「待完成」，用户可以再次提交，服务端于是产生第二个 done 版本与第二条同步项。修法两侧都做：

- 服务端：已经是 `done` 的任务再收到完成事实，只留消息记录，不再推进任务版本，也不再发第二条 `task_updated`——一个任务只有一个完成版本、一条对应同步项，执行次数不累加（`src/along/inbox.ts`）。

### 第五轮：最终审核退回的「缓存升级」

最终审核用附件 `task76-cache-upgrade.mjs` 复现：模拟 GitHub Pages 的 `Cache-Control: max-age=600` 时，已缓存主干 v95 的浏览器在源站切到候选版后，首次在线启动和断网冷重开都执行了主干脚本；两次页面都能正常打开，只看能否打开会误判为升级成功。根因有三层：

1. **静态托管的缓存头**：GitHub Pages 给所有响应 `max-age=600`，浏览器在缓存仍新鲜时直接用旧副本。Service Worker 的回源是 `fetch(event.request)`（默认走 HTTP 缓存），于是源站已经更新，客户端拿到的仍是旧字节——审核脚本里这次访问的源站请求数为 0。
2. **浏览器 24 小时才查一次 Service Worker 更新**：脚本地址不变时，Chrome 在上次更新后 24 小时内不做更新检查，导航和 `register()` 都被节流；已缓存客户端一直跑旧的 `sw.js`，新的回源策略也就无从生效（实测：重启浏览器后直接导航仍然零回源，`caches` 里仍只有 `along-shell-v95`）。
3. **主干与交付分支同为 v95**：主干 `dbcd253` 与本分支各自把资源版本推到 95，两边内容不同、版本号相同，合并后客户端无法靠版本号分辨新旧。

修法（客户端 `along`）：

- `web/sw.js`：预缓存与回源都绕过 HTTP 缓存（`fetch(url,{cache:'no-store'})`），离线时回退 CacheStorage；缓存名推进到 `along-shell-v97`。
- `web/app.mjs`：每次启动强制检查一次 Service Worker 更新（`registration.update()`，绕开 24 小时节流），新 SW 接管后重载一次，让本次启动也用上新资源；每个会话最多重载一次。
- `web/index.html` 与 `ios/AlongHealth/Sources/AlongShellView.swift`：资源版本推进到 v97（`?v=97`、`build=97`）。v96 已被 `feature/task-79-font-scale` 占用，故取 v97，避免两个分支再次撞号。
- 本分支先合入主干 `66bfd52`（无冲突），使版本推进不再与主干的 v95 撞行，后续合并主干不需要手工解冲突。

复测（附件 `task76-cache-upgrade-verify.mjs`，Chrome 158，Node 22，真实 HTTP 源站模拟 `max-age=600`）六条泳道：

### 完成事实已受理但服务端不补发目标快照：任务仍留在「动态任务」里（Bug#1）

问题：点「完成」→ 确认后，服务端已受理这条完成事实，任务却一直留在「动态任务」列表里，刷新也不消失。

根因在服务端与客户端的分工：客户端的「动态任务」只列目标快照里 `status==='open'` 的任务，任务是否完成**只由服务端快照驱动**。当前运行的 Along Agent 收下 `task.completed` 后把任务状态翻成 done（`src/along/inbox.ts` 的 `appendTaskRevision({status:'done'})`），但这一版**不为完成事实补发带目标快照的 `task_updated` 同步项**——那是 TASK-76 的服务端修复 `6fab775`，只存在于 along-superagent 的主干，运行中的那一版没有。于是客户端永远收不到新的目标快照，缓存里的任务仍是 open，卡片就一直挂在当前列表里。

客户端这一侧不再把「列表内容」单方面押在服务端推送上：服务端**受理**了完成事实，这项任务就不再是「待完成」。

- `web/event-workspace.mjs` 增加 `acceptedTaskCompletions()`：台账（`state.completions`）里有这条完成事实、待发队列里已经没有它（已送达）、也没有终态失败——这三条同时成立才算「服务端已受理」。周期任务不记台账（服务端按周期去重，完成的是「本次」），因此周期任务的语义不变：完成本次后它仍留在「动态任务」里。
- `web/app.mjs` 的「动态任务」列表按这个集合过滤：已受理的这一项立刻离开当前列表；服务端补发快照后它在快照里本来就是 done，两处口径一致。台账随本地缓存落盘，刷新或重新进入后这一项仍然不出现。
- 终态回执（被拒／冲突）立刻收敛台账：任务留在当前列表、完成键回来，用户可以重试。收敛放在**同步成功**之后写缓存——同步失败时不写本地缓存这条既有约束不变。

验收：服务端受理完成事实后，这一项立刻从「动态任务」消失，其他项原样；刷新／重新进入后这一项仍不出现；服务端拒收时任务仍可见且完成键回来可以重试；周期任务点完成仍留在列表里（完成的是「本次」）。

### 独立验收退回：终态拒收后完成键被扣住，直到同步恢复（Bug#2）

独立验收（附件 `task86-review.mjs`、`task86-evidence.json`）在「旧 Agent 不补发目标快照」这条链路上确认了主体行为（受理后离开当前列表、切换目标或刷新后仍隐藏、回执丢失时同号重投且只记一次完成），但退回一处缺陷。

**触发条件**：`/events` 返回带匹配事件 ID 的终态 `rejected`，随后 `/sync` 持续返回 503。
**预期**：任务保留，完成按钮立即恢复，刷新后仍可点击重试。
**实际**：任务保留，但完成按钮在失败后和页面刷新后都为 0 个，直到同步恢复才回来（验收证据 `rejectedThenSyncUnavailable`：`buttonWhileFailed: 0`、`buttonAfterReload: 0`、`buttonAfterSyncRecovered: true`）。

根因：上一轮把「完成事实台账」的收敛放在**同步成功之后**（当时为了守住「同步失败不写本地缓存」这条既有约束）。终态拒收已经写在本地失败台账里（`along.events.failed.v1`），但完成事实台账要等一次成功的同步才收敛——同步挂着时，台账仍把这条任务算作「待处理」，`pendingTaskCompletions()` 于是继续扣住完成键。

修法：**终态回执本身就是了结信号，不再等同步。**

- `web/event-workspace.mjs` 的 `pendingTaskCompletions()`：台账里的完成事实若已有终态失败记录（被拒／冲突），就不再算「待处理」——完成键立即回来，用户可以重试。判定只读本地两份记录（待发队列与失败台账），不依赖同步是否成功；回执到了就是终态。同步成功后的台账收敛照旧保留（清理陈旧条目）。

验收：`/events` 终态拒收 + `/sync` 持续 503 时，完成键立即恢复、刷新后仍在、可再次点击并用新事件号重发成功。

### 独立验收再退回：失败记录被淘汰后，被拒的完成事实被当成「已受理」（Bug#3）

独立验收补测（附件 `task86-receipt-retention-probe.mjs`）发现：一条完成事实被服务端终态拒收后，同一工作区再累计 50 条别的终态拒收，最早的失败记录被挤出本地 50 条上限——**任务从「动态任务」里消失了**，状态仍是 `open`，刷新后也不回来，用户既看不到它也点不了完成。

根因：上一轮把「服务端已受理」判定成「不在待发队列里、也不在失败台账里」。失败台账是**有上限的诊断记录**（`web/agent-client.mjs` 的 `EVENT_FAILED_LIMIT = 50`，最旧的会被挤掉），别的任务失败得多了就会把这条挤掉；那时「没在失败台账里」不再等于「被受理过」，被拒的事实被当成了已受理。

修法：**受理这件事由这条完成事实自己的回执说明，不再推断。**

- `web/agent-client.mjs` 的 `flushEventQueue` 逐项带回终态回执（accepted／duplicate／rejected／conflict）。本地失败台账退回它本来的角色：只做诊断记录（「为什么没有生效」），不再当正确性依据。
- `web/event-workspace.mjs` 的完成事实台账记下这条事实自己的 `outcome`（queued／accepted／failed），**按任务记账**：别的任务失败再多也挤不掉它。
- `acceptedTaskCompletions()` 只认 `outcome==='accepted'`；`pendingTaskCompletions()` 把 `outcome==='failed'` 排除在外（完成键回来，用户可以重试）。没有 `outcome` 的旧台账条目沿用旧口径推断（兼容更早的客户端写的缓存）。
- 投递回执在投递后立即记账，与同步成败无关：同步挂着时，被拒的完成照样回到可完成状态。

契约变更：`flushEventQueue` 的返回值多了 `outcomes`（逐项终态回执）。事件队列的两份契约测试按新形状改写，断言未削弱——终态与重试的判定、顺序与幂等语义都不变。

验收：被拒的完成事实在失败记录被淘汰后仍然可见可重试，刷新后也是；只有这次重试获明确受理之后，这一项才从当前列表移除。

验收：旧条目没有回执时，任务可见、完成键回来、刷新与同步返回空页后同样；旧条目的事实还在队列里时仍算待处理、队列保留原事件号；有明确受理回执的条目仍然隐藏已完成项。

### 独立验收再退回：旧 Agent 已落库但客户端没有完成证据（Bug#5）

独立复验（附件 `task86-cache-upgrade-v104.mjs`，真实旧 Agent `d16a98b` 的 Inbox + 临时 SQLite）又找到一个边界：v102 的完成事件**已被服务端受理**（库里任务已是 done、版本 2），但客户端只有 open 快照、没有结果的旧台账。上一轮统一按「没有受理证据就不当已受理」处理——对被拒的事实是对的（可以重试），对**已受理**的事实则把一项做完的任务又摆回待完成，用户会重做一遍；再点一次会带新事件号被第二次受理，旧 Agent 把版本推到 3、完成反馈指针被改写。

修法：**受理与否交给服务端说，不再猜。** 服务端在读取同步项时把**当前**的目标快照挂在同步项上（不是历史快照），客户端回放一次同步就能拿到服务端此刻的真实状态：

- 服务端快照说这项任务已完成：以服务端为准，这项任务退出当前列表（台账一并清掉），用户不再重做，服务端也不会被写第二次。
- 服务端快照说还没完成（或这次没拿到快照）：结果不明，标成 `unknown`——保持可见可重试，也不再反复回放。
- 回放复用既有的同步迁移机制（从序号 0 重拉），一次性代价；旧条目收敛后回放停止。

实测（真实旧 Agent `d16a98b` + 真实目标同步项 + 临时 SQLite + Chrome 158）：v102 客户端完成一次（服务端受理，版本 2）→ 升级到新客户端 → 卡片不再出现，SQLite 版本仍是 2、完成反馈指针没变——服务端没有被写第二次。

**仍存的边界（记录，本轮未修）。** 复核探针的最后一个场景用的是一台**同步项为空**的合成服务端（目标创建时没有对应的 `goal_updated` 同步项，`/sync` 桩也不实现 `tasks_page`），客户端因此读不到服务端的目标快照，无法收敛——那种服务端上只有服务端 Inbox 里的事件号能区分「已受理／明确拒收／未知」，而按事件号查证（用同一个事件号重投，服务端按事件号幂等、不会写第二次）属于 `/events` 通道，正好与同一份探针对两种拒收缓存的断言「升级期间不得发 `/events`」（`eventReplies.length === 0`）冲突。真实服务端有目标的同步项，走读通道即可收敛；这一条属于「读通道拿不到状态」时的取舍，留给阶段流转决定。

回归测试新增两项：服务端快照说已完成时旧条目收敛并退出当前列表；服务端说还没完成时旧条目保持可重试，且收敛之后不再反复回放。回退检测：去掉回放维度 → 两项都变红；去掉「结果不明」的标记 → 「保持可重试且不再回放」变红。

本轮实测：客户端 `npm run check` 915 项：911 通过、0 失败、4 跳过（新增 2 项）。

### 独立验收再退回三处：读取挂起时点出第二笔完成、多页回放跳页、收敛与剪枝顺序（Bug#6）

独立复验（附件 `task86-replay-race-065e7dc.mjs`、`task86-cache-upgrade-v105.mjs`，真实旧 Agent `d16a98b` + 临时 SQLite + Chrome 158）找出三处：

1. **首次读取挂起或返回 503 时，用户点完成会再投一条新的完成事实**：服务端记成第二次受理，版本从 2 升到 3、完成反馈指针被改写、受理数从 1 升到 2。
2. **目标快照落在第二页时，回放跳回旧游标**：旧条目被记成「结果不明」，卡片仍可点——明明单独读 `after_seq=50` 就能拿到 `done` 快照。
3. **收敛与剪枝的顺序反了**：剪枝先把「服务端说已完成」的条目删掉，收敛就来不及丢掉排队里那条完成事实。

修法：

- **未确认状态之前不送达用户新提交的那条**（换了事件号的那条）：服务端状态还没核对过，先送会被记成第二次完成。核对到「服务端已完成」时把它**丢掉**（不必再送达）；核对到「还没完成」才放行；第一次读失败时它留在队列里，等下一次核对——只读核对的入口始终可恢复。
- **台账记着的那条旧事实照常送达**：服务端按事件号幂等，同号重投不会变成第二次完成——旧客户端留下的、可能已被收过的那条，重投是安全的。
- **分页按服务端给的 `nextCursor` 接着取**：旧游标只用于第一页，目标快照落在第几页都能读到。
- **先收敛再剪枝**：收敛要赶在剪枝删掉条目之前，才能丢掉排队里那条完成事实。

### 独立验收再退回两处：done 快照在非末页、新旧回执交错（Bug#7）

独立复验（附件 `task86-replay-race-6d66a1b.mjs`，真实旧 Agent `d16a98b` + 真实回环 API + 临时 SQLite + Chrome 158）又找出两处，两组都让 SQLite 版本从 2 升到 3、受理数从 1 升到 2、完成反馈指针被改写：

1. **目标的 `done` 快照出现在非末页时**：第一页剪枝就删掉了待核对条目，末页收敛已经没有条目可处理，排队里那条新完成事实没被清掉，下一轮照送——服务端记成第二次受理。
2. **同一任务新旧回执交错时**：旧事件回执（`duplicate`）按任务把台账改成 accepted，新事件还在队列里，下一轮又获第二次受理。

修法：**完成事实的下落一确定就清队列。**

- 把「服务端说已完成」的确认从回放结束拆出来，**每页都做**：读完哪一页知道结果，就当场清掉排队里为这项任务等着的完成事实。目标快照落在第几页都能当场清掉。
- **服务端受理了这项任务的完成事实之后**，排队里为这项任务等着的完成事实一律清掉——它已经是第二次完成，多送一次就多记一次。回执按任务归属，用户重新提交、事件号换了也算在这项任务上。

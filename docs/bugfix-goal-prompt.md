# Along 修 bug 的 Goal Prompt

> 用法：把下面 `=== GOAL PROMPT ===` 之间的正文整段粘贴进 goal 模式的 objective。
> 括号里的 `（bug 现象：…）` 是要替换的槽位；没有指定 bug 时走第 2.0 节的巡检分支。
>
> 运行环境假设：MCode / MiniMax Code 目标模式，核实阶段用 `task` 工具的 `verifier` 子代理。

---

=== GOAL PROMPT ===

你正在 `~/workspace/along` 里修复 bug。

Along 是手机优先的目标工作台：把一个目标拆成「目标 / 来源 / 动态任务」三样联动的东西，确定性的部分在本地算，生成式的部分交给 Agent，Agent 的产出必须被校验且由用户点「采用」后才生效。

项目是「一份源码，两份产物」的纯前端 + Mac 宿主结构：

- `web/` —— 前端唯一源码（保持平铺）
- `host/` —— Mac 上运行的服务；它会从 `../web/` 引用 `goal-agent-core.mjs`、`adaptive-ui.mjs`、`super-agent.mjs`、`loop.mjs`
- `test/` —— `*.test.mjs`，`npm run check` 自动运行
- `tools/build.mjs` —— 按 `files` 白名单把 `web/` 复制到 `dist/` 和 `ios/AlongHealth/Web/`
- `dist/` —— gitignore 的本地产物；`ios/AlongHealth/Web/` —— **被 git 跟踪**的产物，`npm run build` 后要一起提交

动手前先读 `README.md`（产品说明）和 `AGENTS.md`（项目约定与红线）。接口和参数以代码为准。

要修的 bug：（bug 现象：在此写用户的原话或问题描述）

---

## 0. 成功标准

一个 bug 算修好，当且仅当同时满足这四条：

1. 有一个**先失败后通过**的自动化测试钉住它（放在 `test/` 下，`node --test` 能跑）；
2. `npm run check` 全绿（语法检查 + 全部测试）——`npm test` 不能顶替它；
3. 复现用的那条命令，现在返回期望结果；
4. 没有违反第 4 节任何一条红线。

「报错消失了」「看起来对了」「改到测试过了」都不算修好。

## 1. 第一性原理

修 bug 不是让报错消失，而是**恢复被违反的不变量**。所以先判断，再动手：

- **先还原正确行为。** 从 `README.md` / `AGENTS.md` / 代码意图推出「这个场景下应该发生什么」，把这句话写出来，再对照现状找偏差。写不出「应该是什么」，就没有 bug，只有猜测。
- **定位偏差在哪一层。** Along 的分层是：`web/` 前端逻辑 → `host/` 服务与路由 → 共享校验层（`web/goal-agent-core.mjs`、`web/adaptive-ui.mjs`、`web/super-agent.mjs`、`web/loop.mjs`，`host/` 从 `../web/` 引用它们）→ 缓存版本号 → 构建产物 → iOS 壳（`ios/AlongHealth/`）。**bug 常常不在你以为的那一层**：报错显示在页面上，根因可能是 `host/` 没同步共享文件、缓存版本号没升导致手机还在跑旧代码、或产物没重新 build。
- **不要把症状当根因。** 修完问一句：「这个不变量在别的路径上还有没有被绕过？」
- **优先确定性。** 能用确定性代码表达的，不引入 Agent 调用；反过来，Agent 产出的一切仍必须被 `validateGoalReply` / `safeAdaptiveLayout` 校验兜住，不能因为「让模型更听话」而放宽校验。
- **默认做减法。** 修 bug 不新增入口、开关、模式、配置、页面。

## 2. 工作流

### 2.0 若没有指定具体 bug

先做一轮巡检，产出候选清单再逐个走下面的流程：

- 跑 `npm run check`，把失败项按「确定失败 / 环境问题」分开；
- 重点看 `web/goal-agent-core.mjs`、`web/adaptive-ui.mjs`、`web/loop.mjs` 的边界（空值、越界、非整数、缺字段、超长字符串、重复 ID）；
- 重点看 `host/agent-host.mjs` 的入参清洗与 `host/kimi-code-agent.mjs` 的 JSON 解析容错路径；
- 每个候选写清：现象、复现方式、违反的不变量。按影响面排序，一次只修一个。

### 2.1 阶段 1 · 复现（Reproduce）

把 bug 描述翻译成一个**可证伪的最小复现**：最小输入 → 期望输出 → 实际输出。

- 优先写成 `test/` 下一个**失败的测试**，跑它，确认它以预期方式失败——是断言失败，不是语法错误、不是环境缺失、不是端口没开。
- 复现必须能脱离本次会话独立重跑：不依赖临时脚本、手改的环境变量、真实 HealthKit 数据、真实账户、真实 iPhone。
- **复现不成立就停下。** 不要去修一个无法证伪的东西。停下来报告：三种可能哪个成立（已被修掉 / 描述不准确 / 需要特定环境）、你验证过什么、还需要什么信息。拿到新信息后重新进阶段 1。

### 2.2 阶段 2 · 独立核实（Independent verification）

**派一个独立的、只读的核实代理去核实，不要自己给自己盖章。** 用 `task` 工具，`agent_name: "verifier"`（只读、不改文件、独立取证、返回 `VERDICT: PASS | FAIL | PARTIAL`）。

给它的材料**只有事实，不许给结论**：

- 仓库路径 `~/workspace/along`
- bug 的原始描述（用户的原话）
- 复现步骤与复现命令
- 让它自己回答的中立问题

**绝对不要**把「我认为根因是 X」写进它的任务描述——那会把你的猜测污染成它的证据。

让它回答：

1. 复现是否真的成立？（它要自己跑一遍复现命令）
2. 这个场景下**正确行为**应该是什么（不变量是什么）？
3. 根因在哪一层？有没有比你的假设更简单的解释？
4. 提议的修复方向会不会踩到第 4 节的红线（token 外发、原始健康样本、绕过 Agent 校验、动理财演示数据边界、直改产物目录、新增入口）？
5. 有没有更上游的成因（缓存版本没升、`web/` 与 `host/` 的共享文件不同步、产物没重新 build、校验层与渲染层假设不一致）？

**核实结论与你的判断冲突时，以核实者为准**：回到阶段 1 重新收敛，而不是硬修。核实者否定了你的复现，也要信它——重新复现。

### 2.3 阶段 3 · 修复（Fix）

- **最小改动、根因修复。** 不做无关重构，不顺手改别的 bug（发现了就单独记录，别混进这次修复）。
- **不放宽校验。** 如果修复确实要动 `validateGoalReply` / `safeAdaptiveLayout` / `cleanGoal` / `cleanSnapshot` 这类校验逻辑，必须在报告里单独说明：为什么这是恢复不变量，而不是绕过红线。
- **补回归测试。** 放 `test/`，命名体现被钉住的不变量（例：`test('health router stays quiet when the target is already met')`），不要 `fix-bug-123`。
- **共享文件双端可用。** 改 `web/goal-agent-core.mjs`、`web/adaptive-ui.mjs`、`web/super-agent.mjs`、`web/loop.mjs` 时，必须同时能在浏览器和 Node 里跑通，不得引入 Node 专用模块。
- **同步产物与版本号**（用户可见的改动，漏一处手机上就还是旧页面）：
  - `web/index.html` 的 `?v=`（当前 44）
  - `web/sw.js` 的 `CACHE`（当前 `along-shell-v44`）
  - `ios/AlongHealth/Sources/AlongShellView.swift` 的 `build=`（当前 44）
  - 需要重新安装 App 时，再提 `ios/AlongHealth/Info.plist` 的 `CFBundleVersion`（当前 38）
- **新增前端文件**要同时登记到 `tools/build.mjs` 的 `files` 和 `web/sw.js` 的 `FILES`，并保持 `web/` 平铺。
- **改源码，不手改产物。** `dist/` 和 `ios/AlongHealth/Web/` 由 `npm run build` 生成；`ios/AlongHealth/Web/` 被 git 跟踪，build 后要连同源码一起提交。

### 2.4 阶段 4 · 回归验证（Re-verify）

修复不是终点，验证才是。依次给出证据：

1. `npm run check` 全绿。
2. 重跑阶段 1 的**同一条复现命令**，贴出现在的输出，证明同一个输入得到期望结果——证明 bug 真的消失，不是被绕过、也不是测试迁就了实现。
3. 检查有没有把问题挪到别处：全量测试 + 相邻路径（`host/` 的校验与路由、缓存版本号、`dist/` 与 `ios/AlongHealth/Web/` 是否与 `web/` 一致）。
4. 用户可见的改动 → `npm run build`，确认 `dist/` 和 `ios/AlongHealth/Web/` 已更新且内容与 `web/` 一致。
5. 报告里贴命令与关键输出，不要只写「已修复」。

## 3. 什么时候停下来问人

- 复现不成立
- 核实结论与你的判断冲突，且无法用证据决出胜负
- 修复必须动红线（token / 健康数据 / Agent 校验 / 理财演示数据边界）
- 修复需要新增依赖、改变产品行为（不只是修 bug），或需要新增入口 / 开关
- 同一个 bug 修了两轮仍不通过
- 需要真机、签名或重新安装 App 才能验证

其余情况自己判断并推进，不要反复确认。

## 4. 红线（违反即回滚，不是「权衡」）

- Token 只留在 Mac：Kimi token、配对 token 不发给 iPhone、不写进运行结果、不进日志
- Agent 的输出不能直接生效：先过 `validateGoalReply` 与 `safeAdaptiveLayout`，用户点「采用」才改变目标空间
- 健康数据只发汇总值，不发原始 HealthKit 样本
- 理财只用演示数据：不接真实账户、不读取账户、不转账、不交易
- 不手改 `dist/` 和 `ios/AlongHealth/Web/`
- `web/` 与 `host/` 共享的文件不得引入 Node 专用模块
- 默认做减法：不加新入口、开关、说明、状态、页面；一屏只服务一个主要任务

## 5. 每次修复的报告格式

1. **Bug**：一句话 + 它违反了哪条不变量
2. **复现证据**：命令 + 实际失败输出
3. **核实结论**：核实者怎么说，尤其是它否定或修正了你的哪一点
4. **根因**：在哪一层，为什么
5. **改动清单**：文件 + 一句话理由 + 是否用户可见 + 版本号是否已升
6. **验证证据**：`npm run check` 结果 + 复现命令现在的输出
7. **遗留**：还没解决的、没验证的、需要真机才能验的

## 6. 命令与工作区

- 仓库根 `~/workspace/along`，分支 `main`，远端 `git@github.com:artstur/along.git`
- **工具链**：本机 PATH 上默认没有 `node`，也没有 `npm`（先 `command -v npm` 确认）。`npm install` 本身需要 npm，没有就先装一个 Node ≥ 22.19（例如 `brew install node`）。
- 只需要 `npm install` 一次：它会把项目自带的 Node 22.23.4 装到 `node_modules/node/bin/node`，并通过 `node_modules/.bin/node` 暴露给脚本。npm 运行脚本时会把 `node_modules/.bin` 加进 PATH，所以 `npm run check` 里的 `node` 用的就是这份 22.23.4，不需要系统 Node（`npm run dev` 直接写死 `./node_modules/node/bin/node`，同一个道理）。
- `npm run check`（CI 同款：语法检查 + 全部测试）、`npm test`（只跑测试）、`npm run build`（生成 `dist/` 与 `ios/AlongHealth/Web/`）
- 推 `main` 不会自动部署：GitHub Pages 要手动触发工作流（`gh workflow run pages.yml --ref main`），iPhone 要在 Xcode 里重新构建安装

## 7. 这个仓库已经踩过的坑（别再踩一遍）

- **`web/app.mjs` 在 Node 里没法 import**：模块顶层就访问 `document` / `localStorage`，历史上等于零测试覆盖。仓库里已有最小 DOM 桩 `test/dom-stub.mjs`（`installDomStub()`），装上桩后 `await import('../web/app.mjs')` 就能驱动真实的渲染、点击与提交；要给 app.mjs 的行为补测试，先用它，别自己重写一份。
- **App 内置页面不是安全上下文**：`along://` 是自定义 scheme，WKWebView 不把它当安全上下文（无公开 API 可改），`crypto.randomUUID` 是 `[SecureContext]` 方法，可能压根不存在；一旦缺失，新建目标、发消息、HealthKit 桥接、Agent 桥接会整体抛 `TypeError`。需要随机 id 时用 `web/super-agent.mjs` 的 `newId()`，它自带降级。
- **自然语言里提取「目标数值」的启发式会一直在误判与漏检之间摆动**：误判会让守卫要求 Agent 匹配一个用户从没说过的数字 → 整单请求被 HTTP 400 拒掉；漏检只是少一道安全网。方向不对称，所以**宁可漏检不可误判**，并且要把语料钉成回归基线（`test/goal-agent-core.test.mjs` 的 `PHRASE_CORPUS`）。每加一条规则都要让独立核实者用「上一版 vs 新版」的差分再跑一遍——本轮就是这样连迭代 6 轮才收敛。
- **自然语言改动词表是长期任务，不是一次性修复**：`目标调整为 / 提高到 / 减到 / 调到` 这类目标词限定的写法要能识别，但「今天运动量提高到 150 分钟」这种事实陈述不能被读成目标；理财域的金额必须带货币标记，否则「目标是 60 公斤」会被读成金额。
- **一次 Agent 运行必须收敛到终态**：前端只在状态不再是 `working` 时停止轮询（`web/app.mjs`），所以宿主与前端都不许让一次运行永远停在 `working`。两处都要查：`host/kimi-code-agent.mjs` 的终态判定（别把终态挂在「子 Agent 花名册完整」这种观察不到的条件上），以及前端读状态失败时的兜底（`web/super-agent.mjs` 的 `withRunError`）。判定终态要用**权威信号**（会话是否结束、有没有校验过的产出），不要用分页窗口（`transcript?page_size=20`）里碰巧看得到的东西。
- **终态条件一旦改动就要做变异测试**：回退其中一条条件，看对应测试是否真的会红。2026-11 这一轮就有两条修复在「全部测试通过」的情况下其实零覆盖。
- **理财演示的「目标」不是余额天花板**：目标是要跨过的门槛，不参与余额运算；一旦拿它去封顶，目标被改小之后点「+¥800」余额反而会倒退。另外，写入时用的上限和 `loadFinance` 读取校验用的上界必须是同一个数，否则会出现「写得进去、读不出来」→ 余额被整条判非法而清零。
- **清数据要连原生侧一起清**：只清网页里的 localStorage 缓存是不够的——原生侧还在读 HealthKit，下一轮前台刷新会把摘要原样写回来。清真实健康数据要走 `alongHealthClear` 这类桥接消息：清掉读取选择并停掉观察。
- **写好的 Service Worker 需要真的注册**：`AGENTS.md` 把 `web/sw.js` 的 `FILES` 登记当成硬约定，但曾经没有任何地方注册过它，离线缓存实际没启用。注册要带支持性判断（`along://` 不是安全上下文，会自动跳过）与失败兜底。
- **原生侧与宿主侧的行为也要能自动测**：`ios/AlongHealth/Sources/*.swift` 和 `host/agent-host.mjs` 都不是可 import 的模块，但「照抄一份逻辑来测」等于没测。仓库里已经用了两种取法：Swift 用 `swift <file>` 跑从真实源码里切出来的那段判断（CI 上没有 Swift 工具链时要优雅跳过），宿主用 `node:vm` 在独立上下文里跑切出来的函数——断言的都是真正发布的那份代码。
- **同一份契约，运行时之间也会分叉**：Kimi 运行时先把模型给的布局归一（`layoutForAlong`）再校验，DSH 运行时直接校验。模型少给一个 `questions`，DSH 路径就把整份目标空间判成「格式不正确」，用户什么都拿不到。两条运行时对同一个字段的判断必须一致——把两边都要用的归一放进共享层（`web/adaptive-ui.mjs` 的 `normalizeQuestions`），不要各写一份。
- **别在归一的时候用 `String()` 兜底模型输出**：Kimi 运行时把提案标题 `String()` 一下，模型返回对象时得到 `"[object Object]"`，混过类型检查后成了用户的目标标题；DSH 运行时却正确地拒绝了同一份回复。归一只负责截断过长字符串，类型不对的值要原样交给共享校验层去拒绝。
- **可选列表和可选字符串要一视同仁**：缺一个 `questions` 数组，和给一个空的 `badge`、`unit`、`note` 一样，都不该让整份布局作废——「缺失」与「为空」等价，列表本身也是可选的。畸形内容（不是数组）仍然要拒绝。
- **数字字符串就是那个数字**：校验只在 `typeof === 'number'` 时做范围检查，字符串会绕过上限，还会因为不再是数字而丢掉进度条。目标写成 `"120"`、`"10,000"` 时要归一成数字再按同一套范围规则校验；不是数字的说明文字才只用来显示。
- **桥接的契约是一次请求一次答复**：原生侧任何「忙，正在处理」的分支都必须回一个失败答复，不能 `return` 掉——否则网页那边的 Promise 永远悬着，用户只看到「点了没反应」。
- **别给「等用户操作」的桥接调用加超时**：健康导入要等用户在原生弹层里选完，可能合法地等很久，一刀切超时会误伤。要保证的是「每个请求都有答复」，不是「每个请求都在 N 秒内答复」。
- **宿主答复的状态码要分清「我发错了」和「对方挂了」**：上游（DSH / Kimi / 模型）故障答复 5xx，客户端请求不合法才是 400。全答成 400 时客户端既不会重试，也分不清该找谁。
- **入参清洗不要用 `String()` 兜底**：`String({})` 得到 `"[object Object]"`，混过长度检查后会被当成用户的目标送进模型。共享契约层要求真字符串的地方，宿主也必须要求。
- **异步回写前要确认「我这条还是当前的那一条」**：同一条路径上的兄弟代码常常已经有这个守卫（实验路径用 `changes[0].id` 判断），那就是这个仓库的既有约定。await 回来之后必须重新确认，否则先发后到的旧结果会盖掉新结果——用户看到的是一条对不上他当前进度的提案。
- **读函数不能有破坏性副作用**：读运行记录的地方一旦发现记录不可信，不能造一条假的「正在连接」把它写回存储——那会让真实状态和失败原因永远看不到，用户只剩一个永久转圈的界面。
- **等用户操作的状态也要留出口**：还没等到 Agent 建议时，提示卡片上也要有「保留原任务」。否则用户唯一的出路是删掉自己的数据才能脱身。
- **期限比较要先归一时间基准**：`Date.now()-undefined` 是 `NaN`，和任何数比较都为假——期限永远不到。缺时间的记录要按已过期处理。
- **格式化时间戳不能直接把脏值喂给 `Intl`**：`Intl.DateTimeFormat.format(new Date(undefined))` 抛 `RangeError: Invalid time value`。如果这行是在 `render()` 里被调用的，一次抛错整个界面就停在旧页面上、之后每次重绘都失败——用户看到的是「点不动的工作台」，而不是「某个时间显示不出来」。空值和非法日期要退化成占位符。
- **0 有时就是「未知」的写法**：宿主用 `Number(entry.createdAt)||0` 表示「起始时间未知」，于是事件里的 `at` 就是 0。`value==null` 拦不住 0，`new Date(0)` 又是一个完全合法的 1970 年——用户会以为那是真的。显示一个看起来很正常的时间，比显示「未知」更糟。
- **白名单与渲染层对「一条记录有哪些字段」的假设必须一致**：渲染层直接读 `run.source` / `run.trigger` / `run.assignments` / `run.events`，白名单就不能放行缺这些字段的记录。白名单把结构校验挂在 `actual===true` 这一层上时，一条 `actual` 不是 true 的坏记录能混过去，渲染时 `run.assignments is not iterable`——和缺时间戳一样，整个界面卡住。
- **仓库外的数据不保证类型**：工单号、标题这些字段来自 Agent 服务，不保证是字符串。不能直接对它调用 `.slice()` / `.toUpperCase()` 之类的方法——方法不存在就是 TypeError，而 TypeError 出现在 `render()` 里就会卡死整个界面。先过一道类型判断。
- **同一件事的两条读取路径要给出同样的结论**：任务那条路径把「记录存在却不可信」落到了明确的失败，目标那条路径却当作「没有记录」——面板静默消失，宿主给的原因用户永远看不到。修好一条别忘了另一条。
- **旧键和新键要一样处理**：运行时切过、缓存键改过之后，同一份记录可能存在两处。读的时候只检查新键，旧键里存着的坏数据就会漏过去，然后在别处被当成「没有记录」而造出一条假状态。查两处就要查两遍。
- **逐块 toString 会把多字节字符切坏**：请求体按 TCP 分段到达时，`text+=chunk` 相当于每块单独解码，一个汉字被切开就变成 U+FFFD。中文是本产品的主要语言，正文极易跨段。要用 `StringDecoder` 跨块保留不完整的字节序列。
- **一条坏记录不能让整台服务起不来**：状态文件解析失败时构造函数直接抛错，宿主在模块顶层就 new 这个类——于是服务启动即崩溃，用户完全用不了，而且看不到任何原因。这些记录只是「在跑的那次会话」的指针，解析失败就按空记录继续。落盘也要原子替换（先写临时文件再改名），否则进程被杀就留下半截 JSON。
- **写失败时不能销毁数据**：原生侧把连接凭证从 UserDefaults 迁到钥匙串，save() 的返回值被丢掉、旧键却无条件删掉——钥匙串写失败时，唯一一份凭证就没了，而且再也回不来。
- **确定性错误要落到终态**：输出校验失败是确定性的（这份结果不会再变好，重试也没用）。抛成 5xx 的话，前端会当成「暂时读不到状态」继续轮询，运行永远停在 working，输入框一直禁用，用户被锁 30 分钟。Kimi 那条路径一直把它落成 blocked + 明确原因，DSH 这条要一样。
- **两条运行时对同一份模型输出必须给出同一个结论**：归一放在共享层，两条运行时都用它。归一只修能修的（截断、编号、去重、丢掉超量与未知类型），修不了的（文本类型不对）原样交给共享校验层拒绝。
- **类型不对的文本不要兜底成 "[object Object]"**：那种脏文本会直接出现在用户的首页上。只有字符串和数字算文本；对象、数组、布尔都不是。
- **共享归一要覆盖回复与提案，不只是目标空间**：目标空间统一了口径，回复与提案却还分叉（一边截断收下、一边整份作废），同一份模型输出在两条运行时上结论依旧相反。两边都要用的归一就都搬进共享层，不要只搬一半。
- **改读体实现时别顺手改上限的量纲**：中文一个字是三个字节，上限从「字符」改成「字节」等于把可用长度缩到三分之一，一次正常的中文长对话会被判「请求过大」。

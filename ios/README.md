# Along for iPhone

Along for iPhone 在内置工作区提供目标聊天、离线缓存和任务提醒，通过原生层配对 Host、管理凭据并读取用户明确授权的 Apple Health 摘要。

本文按构建批次记录协议演进。**Build 54–64 的各段是当时的交付记录**，保留是为了读历史行为，不是现行口径；当前行为看下文「旧 Host 兼容行为」「新协议任务通知」各节，以及 Along 仓库的现行文档。

## 在 iPhone 上运行

固定公网 IPv4 部署使用 Along 构建 78 或更新。在配对页输入 `https://<公网 IPv4>` 与一次性配对码，叶指纹留空。系统会验证公共 CA 证书中的 IP SAN。同地址换叶后沿用原配对。部署步骤见[公网 IPv4 直连](../deploy/README.md#固定公网-ipv4-直连)。

新架构真机验证可先在 Along 根目录运行 `npm run activate`，自动准备专用 DSH profile 并启动 DSH 与 Host。缺少模型或 Key 时终端会询问，Key 隐藏输入且保存在 Mac；后续启动免输。随后在 Xcode 安装 App，按终端显示的地址、指纹和连接码配对。初始化与边界见[一条命令激活](../docs/stage-b-tech-design.md#一条命令激活本机服务2026-11-16)。

App 配对后自动协商事件接入，聊天变更经过服务端校验后同步，无需采用。云端 HTTPS 与本机配对分开；已有个人事件工作区要保留原消息、待发队列与通知，应走[受保护的冷交接](../docs/personal-workspace-handoff.md)，而不是直接重新配对。

1. 从仓库根目录运行 `npm run build`，然后用支持手机系统版本的 Xcode 打开 `ios/AlongHealth.xcodeproj`。在 **Signing & Capabilities** 选自己的 Team，确认 **HealthKit** 已开启；如签名冲突，为新的测试安装使用自己的 Bundle ID。覆盖已有正式安装时不要更换 Bundle ID 或签名身份。
2. 连接并信任 iPhone，按系统提示启用开发者模式，在 Xcode 选择这台手机后点 Run。HealthKit 真实读取需用真机。
3. 配对后从目标的 Apple Health 卡片连接或管理数据，选择类型、预览，并点「导入并允许 Agent 评估」。事件工作区由前后台共用的原生持久队列补传，Host 可达后由 Agent 跟进已有目标。唤醒与锁屏读取受系统限制；解锁或回前台会重试。见[阶段 C](../docs/stage-c-tech-design.md)。

网页界面改动后，从仓库根目录运行 `npm run build`（会同时写入 `dist/` 与 `ios/AlongHealth/Web/`），随后重新构建 App。移动端通过 `along://app/` 自定义协议加载这些内置资源，避免公司网络或 CDN 状态导致启动白屏。

### 一键安装到真机

在本机设置一次设备和签名。用 `xcrun devicectl list devices` 查看 iPhone 的 UDID，用 Xcode 的签名设置核对 Team ID。工程默认 Bundle ID 为 `com.artstur.along`，真机签名使用该 ID 对应的描述文件。这三项由同一仓库的工作树共用。

```sh
git config --local along.iosDevice '<iPhone UDID>'
git config --local along.iosTeam '<Xcode Team ID>'
git config --local along.iosBundleId com.artstur.along
```

连接 iPhone 后，从要安装的检出目录运行 `./tools/install-ios.sh`。脚本生成内置网页资源，签名构建 Release 版，安装到指定真机，再回读并核对 Build 号。相同 Bundle ID 和签名身份的后续安装会覆盖对应 App。不同 Bundle ID 作为独立 App 安装，其本机数据和授权各自独立。Xcode 产物保存在该检出目录的 `ios/build/install/`。启用 APNs 时，Host topic 也使用 `com.artstur.along`。

### 页面滚动

iPhone App 的顶部栏和页面外框固定在屏幕上。目标页与任务详情的长内容在工作区内滚动，聊天继续在消息区滚动，输入框跟随键盘。内置页面使用独立的工作区滚动容器，原生 WebView 关闭外层回弹。任务详情同步刷新时，从该滚动容器恢复同一份结果的阅读位置。普通网页沿用文档滚动。

验收时在短页面的空白处上下拖动，确认顶部栏与页面外框不移动。在长目标页和任务详情滑到末尾，确认内容完整可达且顶部栏固定。打开有多条消息的聊天，确认消息可滚动，点输入框后键盘上方仍可看到输入框。打开一份长任务结果后触发同步，确认阅读位置保留。

## 读取和发送的范围

| 用户选项 | HealthKit 读取 | 导入本机 Along 页面 |
| --- | --- | --- |
| 步数 | 今日步数累计 | `steps` 整数 |
| 健身记录 | 本周 workout，确认情境评估后增加近 28 天汇总 | 本周总量、最近两个完整七日各自记录的分钟数、次数及有记录天数，以及近 28 天的类型与时段分布 |
| 活动消耗 | 今日 `activeEnergyBurned` | `activeEnergyKcal` 整数，单位千卡 |
| 体重 | 最近一次 body mass，确认新版预览后增加最近两个完整七日 | 最近值及两期平均体重。每个有记录的日期取最后一次读数，各日期权重相同 |
| 静息心率 | 近 7 天最近一次 `restingHeartRate` | `restingHeartRate` 整数，单位次/分 |
| 睡眠期间手腕温度 | 近 30 天最近一次 `appleSleepingWristTemperature` | `wristTemperatureC`，绝对温度 °C，保留一位小数 |
| 睡眠 | asleep 阶段，确认情境评估后增加近 7 天汇总，确认新版预览后可对比前后两个七日 | 去重后的分钟数、覆盖天数、各期有记录睡眠日的平均时长、最近一次记录的睡眠结束时间 |

Apple 健康 App 的手腕温度通常展示相对个人基线的偏差；HealthKit 读取的是绝对温度，两者显示口径不同。Apple 睡眠评分没有公开的 HealthKit 读取类型，Along 不会把睡眠时长换算成同名评分；连接页会说明这一限制。

只请求勾选类型的读取权限；不请求写入权限。已选类型用于前台自动检查。已有导入可单独选中「允许 DSH 在后台评估当前目标」，授权仅属于当前目标，沿用该目标已有的数据类型与历史范围。没有可读取记录时，该值显示为“无可读取记录”；HealthKit 不会让读取方区分“没有记录”和“用户拒绝了读取”。用户至少有一项可读取摘要时才能确认导入。当前页面代码把摘要保存在 App 内 WKWebView 的 `localStorage`，不发送原始样本、逐条运动记录、具体睡眠区间或设备信息。若用户主动把 iPhone 与同一 Wi-Fi 的 Mac 上的 Along 服务连接，旧版导入仅允许分享已选的周运动分钟数。要启用情境重排，请通过 Apple Health → 管理 → 读取并预览 → 导入并允许 Agent 评估。手机会向已配对的 Mac 发送勾选类型的汇总、相邻两次观察的变化、当前目标、已有任务与近期反馈。连接信息保存在 iPhone Keychain。

网页健康目标页的「清除本机健康摘要」会一次做四件事：清掉页面 `localStorage` 里的摘要、清掉 App 保存的读取选择（`along.health.selectedTypes`）、停掉 HealthKit 观察、清掉待处理任务票（里面存着真实健身分钟数）。只清页面缓存是不够的——原生侧不停读，下一次前台刷新会把摘要原样写回来。系统层面的读取权限仍需到 iOS「设置 → 健康 → App 与服务 → Along」里撤销。

同一次只允许一个健康导入在进行中：在原生弹层还没选完时再点一次「连接 Apple Health」，这次会明确收到「已有健康数据导入正在进行」，不会被静默丢掉（网页那边的等待会一直悬着，界面看上去像点了没反应）。

## 旧 Host 兼容行为

以下采用、逐目标复评和本机结果通知仅适用于旧 Host；事件工作区使用下文的新协议通知。

在 iPhone 上第一次把目标或动态任务交给 Agent 时，Along 会请求系统通知权限。只有真实 Agent 运行完成、输出通过校验且包含明确下一步时，网页才把结构化通知交给原生 `UNUserNotificationCenter`；相同 Request ID 会在本机去重。点通知会回到对应目标提案或动态任务，通知本身不会替用户采用提案或执行外部操作。

在健康计划的「动态任务 → 补充信息」中，可以把下一步要求交给 Agent。它会结合获准使用的摘要和已有安排，给出具体时刻或询问缺少的信息。睡眠和运动的每日委托会在原任务卡上显示当天的 DSH 建议；只有在系统队列核到同目标、同日及对应时刻，才标记「iPhone 已安排」。睡前准备提醒与建议就寝可在不同时刻；周目标与每日运动分钟分别显示。新决策在 App 前台或下次打开读到工单后可发本机通知。你采用定时任务后，由 iOS 在指定时间提醒，后续采用的改期或取消会同步到系统队列。App 挂起时不会持续轮询 Mac，当前未接 APNs。

## 健康与签名边界

- HealthKit 对没有匹配记录的统计查询可能返回 `errorNoData`；此时界面显示“无可读取记录”，不会把它当作整个连接失败。
- 当前使用 Xcode 个人团队签名。个人团队的配置文件通常 7 天后到期，届时需重新构建并安装。GitHub 提交和 Pages 更新不会自动更新已安装的 iPhone App；移动端需重新同步内置资源并安装。

## 新协议任务通知

对已配对用户，App 按同步完成后的活动目标和未完成任务，将未来的 scheduledAt 排入 iOS。任务改期使用同一系统标识替换，完成、取消、归档和权限变化会清理本协议的预约。已有旧协议委托和用户资料保留。同步回执不等于通知送达，验收分别核对 iOS pending、delivered 以及点击后的目标和任务。

经过 Agent 校验且明确标记的推荐或执行结果使用独立事件身份。已配置远程推送时由 Host 发 APNs，凭据由 Host 保管；设备注册沿用配对连接的原生 HTTPS 信任策略。无远程通道时，已授权的手机在前台同步到仍有效的新结果后可发本机通知。手机把确认过的系统队列摘要回传 Host，用于按实际覆盖去重。iOS 按已经同步并预约的时刻触发本地提醒；离线期间尚未同步的改期需等连接恢复。

使用隔离身份和测试目标验证一次性提醒：创建任务、退出到主屏、等待通知、点开核对目标与任务，再从测试对话取消。正式工作区只做只读验收，不代发聊天、增测试通知或重配对。

已在 Apple 开发者账户启用 Push Notifications 且签名描述文件允许时，签名构建设置 CODE_SIGN_ENTITLEMENTS=AlongHealth/AlongPush.entitlements 与 ALONG_APNS_ENVIRONMENT=development 或 production，与实际签名环境对应。默认描述文件继续支持本地提醒。原生每次启动重新向 Apple 注册，并只向配对的那个 Host 传递设备令牌——传什么、走什么信任策略由**配对连接自己的原生信任策略**决定，不是一律按证书钉死：私网 IPv4 沿用叶指纹钉扎（`legacy-local-pin-v1`），云端 DNS 或公网 IPv4 交给系统信任评估（`system-pki-v1`），策略由主机形态推导，不接受网页自报（见 [CA 方案 §2.2](../docs/iphone-ca-profile-design.md#22-旧连接迁移与-mac-兼容)）。

Debug 真机验收可用环境变量 ALONG_NOTIFICATION_PROBE_TASK 指定真实测试任务的 ID。将 App 送回主屏，等待到时并点击通知，再用 devicectl 读取 App 数据容器 Library/Caches/AlongNotificationProbe.json。该文件只记录指定任务的匿名哈希、系统回读时间、已送达、点击与定位时间。回到前台读取通知中心也可独立验证送达。验收后通过目标聊天撤销测试任务。

## 从旧通知回到本机任务

Build 54 / Web v62 在原来的目标选择器中列出本机已存目标。连接新协议后，从旧版系统提醒点进来，先按旧 goalKey 和 taskId 打开本机记录。任务已调整时显示原提醒和该目标的现有任务。从本机记录可以返回当前目标或通过新协议新建对话。旧目标、任务、授权和配对继续保存在原位置，不将旧内容重写或代发给服务器。

验收覆盖同时存在两套目标、同名不同目标、无当前新目标、重启、断网、通知先于连接恢复、新对话草稿和已撤销的旧任务。原生保留待打开的旧通知直到内置页面接收。新协议回执继续按绑定用户校验。

Build 55 / Web v64 的事件工作区按已保存的目标或任务记录列出本机目标。Apple Health 摘要、理财演示记录、聊天历史和上次选择单独存在时，均不会向该列表添加目标。点开仍有记录的旧通知可返回原任务。目标记录已移除时，页面保留当前目标或对话，并向系统确认已处理该次打开。验收覆盖带有历史数据的空列表、删除目标记录后重启、前台与冷启动通知、以及仍有已存任务的旧用户。

目标执行回执独立保存事件编号。离线重新打开时，旧缓存中已绑定现存目标、把自己的事件编号误存为会话编号的执行回执，在校验后清除这项错误关联，保留回执、目标及任务。验收包含断网冷启动、缓存重写和不合法会话引用的拒绝。

## 已配对工作区的健康摘要与任务提醒说明

Build 56 / Web v65 在已绑定事件工作区中独立保存健康摘要。首次恢复时，若无已存本机健康目标或任务，移除旧页面自动填入的默认运动目标。刷新、重新导入和离线重启均保留用户选过的摘要与真实旧计划。旧版独立页面仍可展示默认运动进度。

任务行读取服务端已校验的下次提醒时间及可选的 `reminderPlan`。Agent 安排的提醒显示下次时间、依据和单次、每日或每周的频次。待补时刻的任务显示服务端问题。验收包含带来源的预约、每周行动日、待补信息、明确关闭、旧任务、无效计划及重新打开缓存。原生通知仍使用现有任务时刻和任务版本。


## Agent 安排的重复提醒（Build 57 / Web v66）

任务同步保留经校验的 reminderPlan（来源、理由、时区与一次/每日/每周规则）。旧快照缺少时区时仍按一次性 scheduledAt 处理。每日和每周计划在系统下一次与首时刻一致时进入 iOS 重复日历队列；首时刻刻意推迟到更远日期时先排一次，后续同步再核对，避免提前提醒。系统回读 actual nextTriggerDate/repeats 后向 Host 报告，Host 仅对确实由手机覆盖的 occurrence 去重。计划安排、系统待发、送达和点击分别验收。

原任务行使用本地可读安排和 Agent 理由，无新增入口。任务完成、取消、关闭提醒或改期沿用稳定任务身份撤回/替换系统排程。调试探针仅只读系统队列并把匿名摘要留在私有本机缓存；pending 为零时清除旧排程字段。APNs 凭据与签名能力缺失时，本轮本地排程不能视为后台新决策远程推送已验收。


## 任务详情与执行记录（Build 61 / Web v70）

新协议首页按目标、动态任务、连接数据源排列，数据源在底部。任务卡保留执行时间、有效定时任务标记和查看详情；推荐方案、来源与可核实的执行记录放在对应任务详情。推荐或任务结果通知进入该任务详情，用户主动反馈时才进入直接聊天。

旧版缓存会从耐久同步仅重放一次补齐执行记录，保持已确认游标、草稿、任务和原提醒。历史补齐不当作新结果再发通知。执行计数只表示已有可信产出／完成事实，不把系统待发队列、重试或任务版本当实际动作。已有推荐的天气／路线分别过期提示保留。

正式用户空间只读验收并保留数据覆盖更新；开发与通知测试用隔离身份，本文早期通过正式目标创建测试任务的旧验收描述不适用于当前交付。实际安装、前台同步、原生系统队列回执和用户视觉观察分别记录。

Build 63 / Web v72 在上述任务详情与目标专属数据源基础上，把“查看详情”收成浅灰小文字链，任务详情主标题与正文使用局部紧凑字号。首页其他字体、既有任务与提醒保持。实际签名／安装记录以发版台账为准。

Build 64 / Web v73 将任务状态与详情文字入口收在同一右边线，统一字号并去掉下划线，添加装饰性小右箭头。任务详情与后台数据行为不变，交付与用户观察以台账记录为准。

设备来源的连接意图在等待 Host 上下文后会再次比对本机耐久记录；若另一个连接实例已更新该记录，旧上下文不得覆盖新意图。每个 open 随稳定 requestId 持久保存 expectedGrantId，重试不会将预期授权改成新值，Host 以当前 grant 比较后才轮换授权。
